# Tape Subsystem Port — Design Spec

## Context

The tape controller (`usim/tape-controller.c`, 959 lines) and tape drive (`usim/tape-drive.c`, 455 lines) are the last major CADR device subsystem never ported to this C# emulator — confirmed by listing `origin/main`'s `usim-cs/` tree directly (no `TapeController.cs`/`TapeDrive.cs` exists) and by `BusAdaptor.cs`'s own tape address-range constants (`TapeControllerLo`/`Hi`, present since Phase 5B) still only feeding a logged, honest placeholder. This spec replaces that placeholder with a faithful port, following the same discipline as every prior device (disk, bus-interface, TV, color TV, Unibus-Map DMA, IOB, diagnostic interface): read the real C directly, port it faithfully, wire it into `BusAdaptor`, test against synthetic data with the same register-interface discipline.

**Worth knowing going in:** the real C's own `README.md` says outright, *"Tape support is under development and is not working yet."* This spec ports what the real C actually does — bugs, documented gaps, and all — not a hypothetical fixed-up version. A faithful port of unfinished reference code is still a faithful port.

## The Milestone

Headless, register-interface-driven, same discipline as every prior device: write a synthetic tape image (per the real C's own documented format and fixture recipe — no real tape image exists anywhere in this repo, confirmed by a repo-wide search), issue real commands (read, write, write-file-mark, space-forward, space-reverse, rewind) through `BusAdaptor`'s real register interface, and confirm the resulting tape-image bytes and status-register bits match hand-computed expectations — the same "operate through the real interface, verify against an independent computation" bar every other device test in this codebase already meets.

**Non-goal:** a real tape image to validate against. Unlike `disk.img`, no equivalent exists for tape anywhere, in this repo or (as far as this research found) readily available elsewhere. Real-tape verification is deferred indefinitely, not something this spec promises.

**Non-goal:** actually booting anything or reading real Lisp tape archives. The CADR boot path never touches tape (same kind of check already done for disk/TV: the boot PROM's own source has no tape references), and no real `.tap`-shaped fixture exists to attempt a real read against regardless.

## Current State (re-verified against the real C source this session, not assumed)

- **Register map**: 6 registers at Unibus octal `0772520`–`0772532` (hex `0x3F550`–`0x3F55A`, already-correct constants in `BusAdaptor.cs`, independently re-verified this session via `0o772520 == 0x3f550` / `0o772532 == 0x3f55a`): MTS (status, offset+0, **read-only**), MTC (command, +2, r/w, GO-triggered), MTBRC (byte/record count, +4, r/w, 2's-complement), MTCMA (current memory address, +6, r/w, low 16 bits — bits 17-16 live in MTC's extended-address field), MTD (data buffer, +8, **read-only**, diagnostic-only, no real semantics — "contains CRC and LRC in tape... not relevant for usim"), MTRD (TU-10 read lines, +10, r/w, diagnostic/IBM-packing-mode status — the real C's own comment says *"if IBM packing mode needs to be supported, this has to be implemented"*, i.e. the real C doesn't implement it either). Dispatch function shape matches every other device: `tape_controller_unibus_read(uaddr, *pv)` / `_write(uaddr, v)`.
- **Command set** (MTC bits 3-1, 3-bit field, all 8 values handled): 0 Off-Line, 1 Read, 2 Write, 3 Write EOF (file mark), 4 Space Forward, 5 Space Reverse, 6 Write/E.R.G. (the real C's own comment: *"for usim there is no concept of ERG so write_erg is handled as same as write"* — fold case 6 into the same code as case 2), 7 Rewind.
- **Execution model, and the one place this spec deliberately diverges from the real C's architecture**: the real C runs tape commands on a **dedicated pthread**, woken by a condition variable when GO is set, with the main Unibus-write call returning immediately and the actual command executing asynchronously. This codebase has no other real threading (the disk-subsystem spec already ruled this out for disk's own non-blocking pthread mode, for the same reason: "this codebase has no other real threading"). **Same ruling here**: port synchronously — writing GO to MTC runs the command inline, to completion, before the write call returns, exactly like `DiskController.Start()` already does. This changes *when* the interrupt fires (immediately after the synchronous call returns, vs. asynchronously from a worker thread) but not *whether* it fires or what state results — same category of faithful simplification as the disk-subsystem's own documented choice, not a new precedent.
- **Fatal (`errx`) paths in the real C** — port these as thrown exceptions, matching the established `DiskUnit`/`DiskController` precedent for the real C's own fatal-misuse guards:
  - `tape_controller_go()`'s `default` case of the function-code switch (unreachable given all 8 values of a 3-bit field are handled — a "should never happen" guard, same category as disk's "shouldn't happen" errx paths).
  - Unknown register offset on read or write (both dispatch switches' `default` — every one of the 6 real offsets is handled, so this is also a "should never happen" guard, not a real-world-reachable path).
  - `tape_drive_seek`'s `SEEK_END`-not-supported and invalid-`whence` paths — internal misuse guards; the C# port's own seek helper only needs to support the two `whence` values the real controller code actually calls with (`SEEK_SET`, `SEEK_CUR`), so these guards may simply not need a reachable equivalent if the C# API shape doesn't expose a `whence` parameter at all (builder's call — see below).
  - `tape_drive_init`'s unit-count-exceeded guard (`unit >= 8`) — this one IS reachable from config (an 9th configured unit), so port it as a real, reachable throw, not just a defensive guard.
- **Non-fatal, recoverable status flags** (all in MTS, never throw): `ilc` (illegal command — set on: write to a read-only tape; a write with record length <4 bytes or not a multiple of 4; GO issued while the controller isn't ready; GO issued while the selected drive isn't online), `nxm` (non-existent-memory/Unibus-map error during the DMA loop — **the real C's own documented gap**: *"this code does not handle eof/eot cases"* directly above both `tape_controller_read`/`_write`, and both DMA loops have a literal `//TODO: move tape to interrecord gap (next record start)` after setting `nxm` — **port this gap faithfully, do not implement the TODO**; tape position is simply left wherever the error occurred), `rle` (record-length error — the tape's real on-media record is longer than the byte count the CPU allocated via MTBRC), `eof`/`eot` (normal status, not errors).
- **The real, concrete mechanism behind "doesn't handle eof/eot cases"** (independently read and traced this session, not just reported secondhand): `tape_drive_read_uint8`/`write_uint8`'s C equivalent returns `false` if the tape position has reached the physical end of the backing file (`pos == mmsz`) — but **`tape_controller_read`/`_write`'s DMA loop never checks that boolean return value at all**. In the real C this means reading past true end-of-file feeds uninitialized stack garbage into the transfer and keeps looping until `mtbrc`/`record_length` reach zero (not a crash, just wrong data silently moved). **C# cannot leave an `out`-style value "uninitialized" the way C can** (same category of forced-deviation as the TV device's invalid-register-offset `value = 0` choice) — see What's Left to the Builder for the exact value to substitute.
- **Tape image format**: documented directly in `tape-drive.c`'s own header comment as `TAPE = FILE*`, `FILE = (RECORD_LENGTH RECORD RECORD_LENGTH)* FILE_MARK`, `RECORD_LENGTH` a 4-byte little-endian length prefix *and* suffix around each variable-length record (minimum 4 bytes, must be a multiple of 4 — the real C's own comment: *"this is not a limitation of wesperco but on LISPM memory addressing is word based"*). **Confirmed, real discrepancy in the real C's own comment vs. its own code** (re-verified directly this session, not just trusted from a research pass): the header comment says *"FILE_MARK = 0x00000000"* / *"The file mark is 0x00000000"* — but the actual `TAPE_FILE_MARK` constant (`tape-drive.h:7`) is `0xFFFFFFFF`, used self-consistently everywhere in both files (`tape-controller.c:386,459`, `tape-drive.c:376,395,421`). **The code is the authority; port `0xFFFFFFFF`, not what the comment says** — exactly the same category of finding (and the same resolution) as the TV device's sync-prom-enable bit, now found a second time in this project on a different subsystem.
- **Backing storage**: the real C `mmap`s the backing file (`MAP_SHARED`). **This spec's own call, matching the already-established `DiskUnit.cs` precedent** (the disk-subsystem spec explicitly chose `FileStream`, not `mmap`, "this codebase has no other real threading" reasoning extends here too — a plain `FileStream` with `Seek`/`Read`/`Write` is the already-proven, idiomatic C# equivalent this codebase already uses): port `TapeDrive.cs`'s backing storage the same way `DiskUnit.cs` already does, not via any `mmap`-equivalent.
- **Tape's DMA target is architecturally different from every device ported so far — confirmed this session, not mentioned in an earlier draft of this spec.** `tape_controller_read`/`_write` move data via `bus_adaptor_unibus_read(mtcma, &data)` / `bus_adaptor_unibus_write(mtcma, data)` — i.e. tape's DMA goes back through the **same generic Unibus dispatcher** every device register read/write already goes through (confirmed: `mtcma` is a raw Unibus address, and `bus-adaptor.c`'s single `bus_adaptor_unibus_read/write` function is the one dispatcher every Unibus-range device, *and* the Unibus-Map memory-DMA translation window, share). This is NOT how `disk-controller.c` works — independently confirmed by direct comparison this session: disk's C calls `main_memory_read_page`/`main_memory_write_page` directly, with zero `bus_adaptor_unibus_*` calls anywhere in `disk-controller.c`. Tape is the first device in this whole project that needs to call *back into* `BusAdaptor`'s own dispatch rather than just expose registers for others to call into. In `BusAdaptor.cs` today, the dispatcher that would need reusing (`ReadUnibus(uint uaddr)` / `WriteUnibus(uint uaddr, uint v, ref bool promDisabled)`, which already correctly routes to every device register range *and* the Unibus-Map DMA translation window) is `private`. **This spec's own call**: promote `ReadUnibus`/`WriteUnibus` to `internal`, and give `TapeController` a back-reference to the owning `BusAdaptor` instance (legal and construction-order-safe to pass `this` from within `BusAdaptor`'s own constructor, the same way `DiskController` already receives a reference to the still-being-wired `UCode`) — `TapeController`'s DMA loop calls `_busAdaptor.ReadUnibus(mtcma)` / `.WriteUnibus(mtcma, data, ref promDisabled)` directly, letting `BusAdaptor`'s existing, already-correct address-range dispatch (including the Unibus-Map DMA path) handle the rest exactly as it already does for every other caller. Do not wire tape straight to `MainMemory` (that would skip the Unibus-Map translation a real memory-mapped DMA write actually needs) and do not reuse the public, paddr-based `BusAdaptor.Read`/`Write` (those apply a paddr→uaddr conversion `mtcma` has already bypassed, being a raw uaddr already).
- **`TapeController` also needs a real `UCode` reference, not just `BusInterface`** — the real C's `tape_controller_assert_unibus_interrupt()` calls `assert_xbus_interrupt()` with interrupt vector `0224`, matching the real interrupt-assertion mechanism `Iob.cs`'s own `AssertUnibusInterrupt(vector)` precedent already uses (confirmed `Iob.cs` takes a `UCode` reference for exactly this). An earlier draft of this spec only mentioned `BusInterface` for tape's error-flag side and understated this second, equally real dependency.
- **EOT tracking**: `eotpos` is computed dynamically from configured tape length (feet) and density (800/1600 bpi, selected by MTC's DEN8 bit) — `eotpos = (length_ft - 4) * 12 * bpi` (the `-4` is a deliberate real-C choice, *"allows writing slightly past nominal EOT, matching real tape behavior"*). `tape_drive_seek` is the single real C function that updates `bot`/`eot` status flags as a side effect of every position change (clamping `pos` to `[0, fileSize]`, never going negative or past the file's actual byte length) — port this exact clamping-with-side-effect-flags behavior, don't split it into separate "clamp" and "update flags" steps that could drift apart.
- **Config**: the real C's own parser (`ucfg.defs`) defines an `[tape]` section with keys `tape0` through `tape7` (8 units, `NUMBER_OF_TAPE_DRIVES` in `tape-drive.h`), each value a string `[LENGTH,][MODE,]TAPE_FILE` (`LENGTH` in feet, default 2400; `MODE` is `ro` or `rw`, default `rw`). **This is the authoritative real-C config grammar to port** — confirmed directly from the parser definition, independent of any `.ini` file's actual current contents (the `usim/usim.ini` file sitting in this repo turned out, on inspection, to already be shaped like the C# port's own `[Paths]`/`[Devices]`-style config, not the real C parser's `[tape] tape0=...` grammar — a red herring, not a blocker; don't let it steer the port's config shape). Wire this through `Program.ApplyConfiguration` → `UsimState`, the same live config path the disk subsystem's own `[disk]` section already uses (not the dead `ConfigManager`).
- **Config error handling is a GENUINE, CONFIRMED DIVERGENCE from the disk subsystem's own rules — not a transferable precedent.** Independently traced `tape_drive_init` line by line this session (not just reported secondhand): the **only** fatal (`errx`) path is `unit >= NUMBER_OF_TAPE_DRIVES` (a config bug, 9+ units configured). Every other failure — an empty/malformed config string, a tape file below the minimum required size for its configured length, `open()` failure, `mmap()` failure — logs a `WARNING`/`NOTICE` and returns early, leaving that unit merely `online = false`. **`disk-unit.c` really does `errx` on the equivalent failures (confirmed by direct comparison this session) — tape's real C is deliberately more lenient than disk's, not the same rule.** An earlier draft of this spec claimed tape matches disk's "fatal if missing" rule; that claim was wrong and is corrected here. Port tape's own real behavior: a missing/undersized/unopenable tape-pack file is a **non-fatal, logged, leave-the-unit-offline** condition — only a unit-count overflow throws. (One real-C wrinkle that can't be ported byte-faithfully: the real C calls `stat()` without checking its return value, so a missing file's size check actually runs against uninitialized `struct stat` data — undefined behavior, not a defined "file missing" branch. C# must assign a defined outcome here; treat "file doesn't exist" the same as "undersized" — a non-fatal, logged, offline outcome, matching the real C's overall leniency even though the exact mechanism can't be reproduced.)

## Design

### `usim-cs/TapeDrive.cs` (new file)

Per-unit state (one instance per configured unit, up to 8 — matches `DiskUnit.cs`'s own per-unit-instance pattern): `Unit`, `Configured`, `Online`, `ReadOnly`, backing `FileStream?`, `FileSize`, `Bpi` (density, set by the controller per the DEN8 bit), `EotPos` (recomputed whenever `Bpi` changes), `Pos` (current tape position, bytes from BOT), `Bot`, `Eot`, `Rws` (rewind status — cleared when BOT is reached, matching the real C's own documented rewind-status semantics).

Methods, faithfully named after their real-C counterparts where there's a clean 1:1 mapping (matching this codebase's established naming convention — `DiskUnit.Seek`/`.Read`/`.Write` map directly to `disk_unit_seek`/`_read`/`_write`): `Configure(lengthFeet, mode, filename)` (parses the real grammar, fatal if the file doesn't exist or the unit index is out of range, matching the disk-subsystem's already-established fatal-vs-silent-skip rules), `SetBpi(bpi)`, `Seek(offset, relative)` (the C#-idiomatic two cases the real controller code actually needs — absolute and relative-to-current; no `SEEK_END` equivalent needed since nothing in `TapeController` ever calls with it), `ReadByte(out byte value)` / `WriteByte(byte value)` returning `bool` for success (mirroring the real C's own return-value convention, so `TapeController`'s port can choose — see What's Left to the Builder — exactly how to handle a `false` return, faithfully reproducing "doesn't handle eof/eot" rather than silently adding a guard the real C doesn't have), `ReadUInt32`/`WriteUInt32` (4-byte little-endian, for record-length preamble/postamble and the file-mark sentinel), `WriteRecordLength(length)`, `WriteFileMark()`, `RewindAndOffline()`.

### `usim-cs/TapeController.cs` (new file)

Register state: `Mts` (status, computed/encoded on read from live flags — not stored as a raw value, matching `DiskController.EncodeStatus()`'s own established pattern of recomputing from live sub-state on every read rather than caching), `Mtc` (command register raw value plus its decoded sub-fields: `Fun`, `Slt`, interrupt-enable, etc.), `Mtbrc`, `Mtcma`, `Mtd` (write-only-meaningful, read-back-is-last-written, diagnostic-only), `Mtrd` (same diagnostic-only treatment).

Public surface, matching every other device's established register-interface shape (`DiskController.Read(offset)`/`Write(offset, v)`): `Read(uint offset, out ushort value)`, `Write(uint offset, ushort value)` — **no `ref bool promDisabled` parameter**: independently confirmed this session by reading `tape-controller.c` in full that it never touches `machine_state.promdisabled` anywhere, unlike `DiagnosticInterface`'s mode register — don't copy that signature shape over unthinkingly. `BusInterface.SetUnibusNxm()` (already exists) is the real error-flag mechanism to reuse for the two "should never happen" unknown-register-offset guards.

Private methods, one per real-C function, same synchronous-call structure as `DiskController.Start()`→`StartRead()`/`StartWrite()`/etc.: `Go()` (the command dispatch — **independently confirmed this session, tracing `tape_controller_go()` directly**: GO issued while the selected drive is offline sets `Mts.Ilc = true` and returns, the same "set an error flag, don't throw" shape as every other ILC-setting path — NOT disk's own, different "silent no-op into a log line" choice; the two devices genuinely diverge here, confirmed by reading both, not assumed to match), `Offline()`, `Read()`, `Write()` (handles both function codes 2 and 6, per the real C's own fold), `WriteEof()`, `SpaceForward()`, `SpaceReverse()`, `Rewind()`.

### `BusAdaptor.cs` wiring

**Re-verified against the actual current file this session** (this spec's research happened on a stale branch that predated the TV/color-TV/IOB/diagnostic-interface/idle ports — all now real, merged, and present): `BusAdaptor`'s constructor is `BusAdaptor(BusInterface busInterface, MainMemory mainMemory, UCode ucode)`, and every other post-construction-wired device (`DiskController`, `Tv`, `ColorTv`, `Iob`) follows the exact same `private X? _x; public void WireX(X x) { _x = x; }` pattern — `TapeController` should follow this same established convention, not invent a different one: `private TapeController? _tapeController; public void WireTapeController(TapeController tapeController) { _tapeController = tapeController; }`.

Replace the current logged-placeholder fallback for `TapeControllerLo..Hi` (already-correct constants) with a real dispatch to `_tapeController`, same structural pattern every other wired device's dispatch already uses in `ReadUnibus`/`WriteUnibus`.

**The DMA back-reference** (see Current State's DMA-architecture finding): promote `ReadUnibus`/`WriteUnibus` from `private` to `internal` (this codebase already has precedent for promoting a `BusAdaptor` range constant from `private` to `internal` when something outside the class needs it — `UnibusMappingLo`/`Hi` are already `internal` for exactly this kind of reason), and give `TapeController` a constructor parameter for the owning `BusAdaptor` instance, wired via `WireTapeController` the same way the others are (not the constructor itself, to avoid a circular construction-order requirement — `BusAdaptor` must already exist before anything can call `WireTapeController` on it, so `TapeController`'s own constructor takes `BusAdaptor` as a parameter and `TapeController` is constructed, then wired, after `BusAdaptor` itself — mirroring exactly how `DiskController` already receives its own `BusAdaptor`-adjacent dependencies in this codebase's established construction order).

### Config wiring

A new `[tape]` config section (8 keys, `tape0`..`tape7`), parsed in `Program.ApplyConfiguration`, populating a `UsimState.TapeUnits` array (or equivalent) the same shape as the already-established `UsimState.DiskUnits`, then `TapeController.ConfigureUnit(unit, lengthFeet, mode, filename)` called from wherever `MachineControl` already does the equivalent disk-unit configuration loop.

### Tests

New `TapeDriveTests.cs` and `TapeControllerTests.cs`, same established conventions (`static class`, `RunAllTests()`, own `--test-*` CLI switch, wired into `--test-all`) as every other device in this codebase. At minimum: a synthetic tape image built per the real C's own documented fixture recipe (a handful of variable-length records plus a file mark, built directly in test code — no external fixture file needed, matching how `DiskUnitTests.cs` builds its own sparse synthetic disk images inline rather than shipping a binary fixture); register round-trips through `BusAdaptor`'s real interface for at least one instance of every command (Read, Write, Write EOF, Space Forward, Space Reverse, Rewind, Off-Line); the file-mark sentinel's real value (`0xFFFFFFFF`) exercised directly, not just trusted from the spec text; the record-length-not-a-multiple-of-4 and read-only-write ILC-setting paths; an NXM-during-transfer path (confirm it sets the flag and leaves tape position wherever the error occurred — the undocumented-gap behavior, not an invented recovery); and the EOT-clamping-with-side-effect-flags behavior at the exact boundary (matching the "last valid word" boundary-testing discipline already established for the disk and TV devices' own test suites).

## Constraints

- No new NuGet dependencies.
- Synchronous execution only — no threading, no condition variables. GO triggers inline, synchronous execution, matching the disk subsystem's own already-ruled-on precedent for exactly this kind of real-C threading mismatch.
- `FileStream`, not any `mmap`-equivalent, for the backing tape-image file — matching `DiskUnit.cs`'s own already-established choice for the identical real-C-uses-mmap situation.
- Port the real C's own documented gaps faithfully — do not implement either of the two `//TODO` comments in the real C's own source (interrecord-gap repositioning after an NXM error; IBM packing mode via MTRD). Named and not hidden, same convention every prior phase has used for deliberately-left gaps.
- The file-mark sentinel is `0xFFFFFFFF` — the real C's own header comment claiming `0x00000000` is wrong; the code (used consistently in both files) is the authority. Do not trust the comment if you re-read the real C yourself during implementation.
- **Only a unit index ≥ 8 is fatal (throw) at configure-time.** A missing/undersized/unopenable tape-pack file is explicitly NOT fatal — leave that unit offline with a logged warning, matching the real C's own (deliberately more lenient than disk's) behavior. Do not copy the disk subsystem's "missing file is fatal" rule here — confirmed this session, by direct comparison of both real C files, that tape and disk genuinely diverge on this point.
- Every octal/hex literal and bit position in this spec was read directly from `usim/tape-controller.c`/`usim/tape-drive.c`/`usim/bus-adaptor.c` during this spec's own research this session (not transcribed from an old summary), including the one real discrepancy found and resolved (the file-mark sentinel) — consistent with this project's standing rule to re-verify against the real C source, not trust prior text.

## What's Left to the Builder

Several items an earlier draft of this spec left open were independently resolved this session by re-reading the real C and the current codebase directly (not guessed) — recorded above in Current State / Design, not repeated here. Genuinely still open:

- **The exact substitute behavior for the EOT-mid-transfer gap** — confirmed the real C's DMA loops increment `mtbrc`/decrement `record_length` unconditionally regardless of `ReadByte`/`WriteByte`'s success, so the loop always terminates in bounded iterations even past true end-of-file (no infinite-loop risk) — but the exact choice of *what byte value* to feed in on a failed read (any fixed value, e.g. `0`, faithfully reproduces "wrong data silently moved" — the real C's own bug, not a new one) is still the implementer's call; document whichever value is chosen as a deliberate, honest deviation, same convention as the TV device's invalid-offset `value = 0`.
- Exact field names/types for `UsimState.TapeUnits` and where in `MachineControl`'s existing boot sequence the per-unit `TapeController.ConfigureUnit` loop belongs — mirror the disk subsystem's own already-shipped equivalent code exactly, don't invent a new shape.
- Whether `TapeDrive`'s own seek helper needs a `relative`/`whence`-style parameter at all, or can be two plain methods (`SeekAbsolute(pos)` / `SeekRelative(delta)`) — the real C's `tape_drive_seek` only needs to support `SEEK_SET`/`SEEK_CUR` for this port's own call sites (confirmed: `SEEK_END` and any other `whence` value only appear in the real C's own internal-misuse guards, which don't need a reachable C# equivalent at all if the API shape never exposes a raw `whence` parameter in the first place).
